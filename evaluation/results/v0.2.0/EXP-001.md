# EXP-001: Data-bound vs. step-bound hypothesis (v0.3 specification)

**Status: specification only. No training was performed or requested by this
document.** This is a pre-registered experiment plan for a future v0.3 run;
executing it is a separate, explicit decision.

## Hypothesis

v0.2.0 trained for 20,000 optimizer steps (655,360,000 tokens processed,
effective tokens/optimizer step = batch_size(16) × grad_accum_steps(4) ×
block_size(512) = 32,768) on WikiText-103-raw-v1, a corpus of ~117M training
tokens at this tokenizer's 16k vocabulary. At that ratio, the model has seen
each training token roughly 5.6 times (655.36M processed tokens / 116.995555M
train tokens ≈ 5.6 epochs).

**CTO hypothesis: the model is more data-bound than step-bound.** Repeating a
~117M-token corpus ~5.6 times plausibly produces diminishing returns from
further steps on the *same* data, relative to what the same compute budget
would buy on a larger, more diverse corpus. EXP-001 tests this by changing
only the training corpus, holding every other variable fixed, rather than
training v0.2.0's data for more steps.

**Important open question this experiment does *not* resolve on its own:**
whether the v0.2.0 best checkpoint occurred at step 20,000 or earlier is
still marked NOT VERIFIED as of this document (see the "True best checkpoint
step" line in `docs/EVALUATION_v0.2.0.md`, section A) — that verification
should complete before EXP-001 is greenlit, since an early best-step would
itself support (or weaken) the data-bound hypothesis independent of a corpus
change.

## Expected improvement

Lower validation perplexity and lower bits-per-byte (BPB) at a matched or
lower training-token budget than v0.2.0, on the same fixed evaluation harness
(`evaluation/evaluate.py`, `evaluation/eval_prompts.json`) — i.e. more signal
learned per token seen, not just more tokens seen.

## Single changed variable

**Training dataset.** Everything else below is held fixed to v0.2.0's
values.

## Changed variable: dataset

| Field | Value |
|---|---|
| Dataset name | FineWeb-Edu (sample subset), proposed — **candidate only, not committed** |
| Dataset license | **NOT VERIFIED here.** FineWeb-Edu is published by HuggingFace/Hugging Face FineWeb team under ODC-By 1.0 at the time this repository's v0.2.0 dataset notes were last updated; this must be re-confirmed from the dataset's own HuggingFace card immediately before use, not assumed from this document, since license terms and dataset cards can change. |
| Dataset size plan | Match v0.2.0's training-token budget: sample a subset targeting ~117M-150M raw tokens after this project's own tokenizer encodes it (i.e. comparable order of magnitude to WikiText-103's training split, not FineWeb-Edu's full multi-trillion-token scale) |
| Dataset SHA plan | Compute and record SHA-256 of the frozen sampled subset file at data-preparation time, the same way `data/wikitext103_train_v16000.npy`'s provenance should be recorded — no SHA exists yet because the subset has not been drawn |
| Data suitability check | Before sampling: confirm license terms, confirm the subset is disjoint from any data used to train the tokenizer's vocabulary (to avoid a train/eval leakage argument), and spot-check a sample of documents for basic quality (per this repo's `clean_records` filters) |

**Tokenizer note:** the tokenizer itself is *not* the changed variable in
EXP-001 (only one variable changes, per the pre-registration rule). Re-using
the exact v0.2.0 tokenizer on a new corpus is a deliberate simplification —
it will likely produce a higher out-of-vocabulary / less-efficient encoding
on FineWeb-Edu than a tokenizer trained on that corpus would, which is a
known, accepted confound of "hold the tokenizer fixed." If EXP-001's result
is ambiguous, a fair follow-up experiment (not part of this spec) would
retrain the tokenizer on the new corpus as its own single-variable change.

## Pre-registered thresholds (defined before any run starts)

| Metric | v0.2.0 baseline (frozen, see `docs/EVALUATION_v0.2.0.md` §G) | EXP-001 threshold |
|---|---|---|
| Validation perplexity | harness value from this branch's verified re-run (NOT the training-status figure — see §B vs §A in the evaluation report) | must be **lower** than the frozen baseline by a pre-registered margin of at least 5% relative, to count as a meaningful win (not noise) |
| BPB | harness value from this branch's verified re-run | must be **lower** than the frozen baseline |
| Repetition (`mean_repeated_ngram_frac`) | harness value from this branch's verified re-run | must not be **worse** than the frozen baseline by more than 10% relative (a perplexity win that comes from more repetitive degeneration does not count as a win) |

Exact baseline numbers are filled in from `docs/EVALUATION_v0.2.0.md` §G
once that section's harness re-run is verified (see NOT VERIFIED markers
there) — this spec intentionally does not hard-code a number that has not
been confirmed in this branch.

## Definition of done

EXP-001 is "done" only when all of the following are true and each is
backed by an actual file/log, not a summary:
1. The sampled dataset subset exists with a recorded SHA-256 and a documented
   sampling procedure.
2. A full 20,000-step training run completes (or is explicitly stopped early
   with a documented reason), using the fixed hyperparameters above, with
   `training_status.json` showing `state: completed` (or the stop reason).
3. `evaluation/evaluate.py` is re-run against the resulting checkpoint with
   the same fixed prompt set and seed, producing perplexity, BPB, and
   repetition metrics.
4. The pre-registered thresholds above are evaluated against the actual
   result — not restated as having "improved" without the comparison.
5. A short report (following the same structure as
   `docs/EVALUATION_v0.2.0.md`) is committed with the honest outcome,
   including if the thresholds were **not** met.

## Failure condition

If, after the full 20,000-step budget, validation perplexity and BPB are not
both better than the frozen v0.2.0 baseline (by the margins above), EXP-001
is a **negative result** for the data-bound hypothesis at this scale and
budget — not a reason to silently extend the run past the pre-registered
budget or to quietly drop the thresholds. A negative result should be
recorded as such; the next reasonable step would be to revisit whether the
confound noted above (reused tokenizer) explains it, rather than to declare
the hypothesis false outright.
