# EXP-001: Is v0.2.0 data-bound? (v0.3 specification)

**Status: specification only. No training was performed or requested.** This is a pre-registered
plan, and executing it is a separate, explicit decision.

## Evidence this spec starts from (all verified; see `docs/EVALUATION_v0.2.0.md`)

**Budget and repetition.**

- v0.2.0 trained for 20,000 optimizer steps at 32,768 tokens per step (batch 16 × grad_accum 4 × block 512).
- That is 655,360,000 tokens processed on a 116,995,555-token WikiText-103 training stream.
- So the model saw each training token about 5.6 times.

**Where the best checkpoint landed.** The true best checkpoint is at step 19000, not 16000.

| Step | Validation loss | Source |
|---|---|---|
| 19000 | 3.18217 (best) | eval log |
| 19500 | 3.19944 | eval log |
| 20000 (final) | 3.191914 | training status |

- **The loss was still improving late.** It kept falling until step 19000, in the final low-learning-rate phase of the cosine schedule.
- **The last 1,000 steps are flat.** They are flat within the noise of the random-batch estimate.
- **So the evidence is ambiguous.** It does not show an early plateau, and it does not rule out data-boundness either, because the LR decay confounds any plateau reading.

**Frozen baseline (harness, WikiText-103 validation).**

| Metric | Value |
|---|---|
| Validation loss | 3.175354 |
| Perplexity | 23.9353 |
| Bits per byte | 1.040343 |
| `mean_repeated_ngram_frac` (greedy, 80 tokens) | 0.0963 |

## Hypothesis

**The CTO hypothesis is that v0.2.0 is limited more by the amount of unique data than by the
number of optimizer steps.** If true, spending the same compute budget on a larger, more diverse
corpus should give a better model than spending it on about 5.6 passes over WikiText-103.

## Single changed variable

**The training corpus.** WikiText-103 (about 117M tokens) is replaced by a mixed corpus:

- all of WikiText-103 train, plus
- a FineWeb-Edu sample of about the same size (target 117M tokens after encoding with the v0.2.0 tokenizer).

That doubles the unique training tokens to about 234M, so the same 20,000-step budget becomes
about 2.8 epochs instead of 5.6. WikiText-103 stays in the mix so the frozen WikiText validation
baseline remains an in-distribution comparison.

## Evaluation procedure and pre-registered thresholds

Both models are evaluated on both validation sets. v0.2.0's FineWeb-Edu numbers need an eval-only
run on the new held-out split, with no training.

| Metric | Pass condition for EXP-001 |
|---|---|
| **Primary: FineWeb-Edu held-out BPB** | at least 5% lower (relative) than v0.2.0 on the same split |
| **Guardrail: WikiText-103 validation BPB** | no more than 2% higher than the frozen 1.040343. Half the training data changed domain, so a small in-domain cost is tolerated; a larger one fails. |
| **Guardrail: WikiText-103 perplexity** | reported against 23.9353 and bound by the same 2% limit through BPB |
| **Guardrail: repetition** | `mean_repeated_ngram_frac` (greedy, 80 tokens, fixed prompts) no more than 0.1059, i.e. at most 10% relative worse than 0.0963 |

These thresholds are fixed now and must not be changed after results are seen.

## Cost estimate

About **21 T4-hours**. This assumes v0.2.0's measured 8,731.8 tokens/s holds and the same
655,360,000 tokens are processed. That is roughly 6–7 free Kaggle GPU sessions using the existing
resume pipeline. Data preparation, the FineWeb-Edu download slice, and encoding are extra CPU time
not included here.

## Definition of done

1. The dataset slice, held-out split, SHA-256s, and sampling log exist.
2. A 20,000-step run completes (`training_status.json` state `completed`), or is stopped with a documented reason.
3. `evaluate.py` and BPB are run on both validation sets for both v0.2.0 and EXP-001.
4. Each pre-registered threshold is reported as pass or fail, with the actual numbers.
5. A report in the same structure as `docs/EVALUATION_v0.2.0.md` is written, including a negative result if that is the outcome.

## Failure condition and known confounds

**What counts as a negative result.** If the primary threshold fails, the result is negative for
this form of the data-bound hypothesis at this scale and budget. It is not a reason to extend the
run or change the thresholds.

**Known confounds (accepted, not controlled):**

- **Reused tokenizer.** The WikiText-trained tokenizer is likely less efficient on FineWeb-Edu. BPB partly compensates, since it is per byte, but the model sees fewer bytes per step.
- **Domain shift.** The mixed corpus changes the domain as well as the amount of unique data.

**Alternative considered and not chosen.** Train on half of WikiText-103 for the same 20,000 steps.
This would test data-boundness in-domain with no new data, but it only diagnoses the problem and
cannot yield a better model.
