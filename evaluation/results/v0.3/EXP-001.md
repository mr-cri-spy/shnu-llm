## 1. Hypothesis

v0.2.0 is limited more by the amount of unique training data than by its optimizer-step budget.
If that is true, the same 20,000-step budget spent on a corpus with twice as many unique tokens
should produce a better model than 5.6 passes over WikiText-103.

The v0.2.0 evidence is ambiguous, which is why this is an experiment and not a conclusion:

- **The loss improved late.** The best validation loss was reached late, at step 19000 (3.18217).
- **The end was flat.** The last 1,000 steps were flat within estimation noise (19500: 3.19944; final: 3.191914).
- **The LR schedule confounds it.** The cosine learning-rate decay makes any plateau hard to attribute to data rather than schedule.

Source: `docs/EVALUATION_v0.2.0.md`, §A.

## 2. Single changed variable

**`training_corpus`**, and nothing else.

- **v0.2.0:** WikiText-103 only, 116,995,555 training tokens.
- **EXP-001:** the same WikiText-103 training tokens plus a FineWeb-Edu slice of the same size, 233,991,110 training tokens in total.

Two `shnu_config` fields also differ from v0.2.0, but they are run identity, not experimental variables:

- **`version`** is `"v0.3"` instead of `"v0.1"`. v0.2.0 carried the stale `"v0.1"` label; see §A of the evaluation report.
- **`out_dir`** is a new directory, so the v0.2.0 run can never be written to.

The validator enforces that no other field differs.

## 5. Target corpus

| Component | Source | License | Training tokens |
|---|---|---|---|
| WikiText-103 | the existing v0.2.0 stream `wikitext103_train_v16000.npy`, reused unchanged | CC BY-SA 3.0 | 116,995,555 |
| FineWeb-Edu | `HuggingFaceFW/fineweb-edu`, config `sample-10BT` | ODC-By v1.0 plus CommonCrawl Terms of Use | target 116,995,555 |
| **Combined** | dataset key `wikitext103_fineweb_edu_mix` | | **target 233,991,110** |

**Data preparation rules (all required before training).**

- **Reuse the WikiText-103 streams unchanged.** The WikiText-103 train and validation streams must be the exact v0.2.0 `.npy` files; they are not re-prepared. The v0.2.0 validation set is the last 1% of the tokenized WikiText-103 train split (1,181,773 tokens, SHA-256 `058b710795d4a8dd6b7655a635eda645d7009b2112cccd53e7712783e5eddcb8`). Re-preparing WikiText could move that boundary and leak validation text into training.
- **FineWeb-Edu training slice.** Stream documents in dataset order, apply the repository's `clean_records` filter, and encode with the v0.2.0 tokenizer. Stop at the first document boundary at or after 116,995,555 tokens. Record the document count, the document-ID list and the SHA-256 of each output file.
- **FineWeb-Edu held-out set.** Take the next disjoint block of documents from the same stream (target 1,181,773 tokens) as `fineweb_edu_heldout`. It is never trained on.
- **Mixing.** Split both training streams into documents at `<eos>`, order them with `numpy.random.default_rng(1337).permutation`, and concatenate. The result is 50/50 by token count and contains every token of both streams exactly once.
- **Training-loop validation stream.** `wikitext103_fineweb_edu_mix_val_v16000.npy` is a byte copy of the v0.2.0 WikiText validation stream, so its SHA-256 is `058b7107…e5eddcb8`. In-loop evaluation and `checkpoint_best` selection therefore use exactly the v0.2.0 validation data.
- **Licence.** Re-check the FineWeb-Edu dataset card immediately before download, and carry ODC-By attribution into the dataset metadata.
- **Reproducible order.** Downloading is refused until `dataset.components[fineweb_edu].revision` pins a dataset revision, because the document order depends on it. Preparation can also read a local JSON-lines export (`--fineweb-jsonl`), whose own SHA-256 is recorded.
- **Implementation.** `scripts/prepare_exp001_data.py` performs all of the above. It verifies the tokenizer hash, the WikiText validation hash and both WikiText token counts before writing anything, and it refuses to overwrite existing outputs. It writes `EXP001_DATA_MANIFEST.json` with the SHA-256, size and token count of every file. It also checks the WikiText train stream's SHA-256, size and dtype against the pinned values.
- **FineWeb-Edu cleaning (new in EXP-001).** FineWeb-Edu documents go through the `clean_records` rules with `min_chars` 64. The value 64 is an EXP-001 parameter for FineWeb-Edu only. It equals the current `prepare_data.py` default, but the `min_chars` actually used for the v0.2 WikiText preparation was not recorded and is **UNKNOWN**, so 64 is not claimed as a frozen v0.2 value. The WikiText stream is reused byte-for-byte and is never re-cleaned, so this parameter cannot affect it.

## 6. Token budget and repetition

| | v0.2.0 | EXP-001 |
|---|---|---|
| Tokens processed (20,000 × 32,768) | 655,360,000 | 655,360,000 |
| Unique training tokens | 116,995,555 | 233,991,110 (target) |
| Expected epochs (processed ÷ unique) | 655,360,000 ÷ 116,995,555 = **5.6016** | 655,360,000 ÷ 233,991,110 = **2.8008** |

The only intended difference is that each training token is seen about 2.8 times instead of
about 5.6 times, while the compute budget stays the same.

**Estimated cost.** About 20.8 T4-hours (655,360,000 tokens ÷ the v0.2.0 measured 8,731.8
tokens/s), or roughly 6–7 free Kaggle GPU sessions.

## 7. Acceptance and evaluation procedure

**Who is evaluated, and where.** Both the v0.2.0 checkpoint (evaluation only, no training) and
the EXP-001 final checkpoint are evaluated on both validation sets:

- **WikiText-103 validation:** the frozen baseline set.
- **FineWeb-Edu held-out:** the new set.

**Procedure.** Use the same harness, seed 1337 and eval_iters 100, report
BPB for each set, and run the fixed-prompt greedy repetition metric at 80 tokens.

| Metric | Pass condition (pre-registered; fixed before training) |
|---|---|
| **Primary:** FineWeb-Edu held-out BPB | EXP-001 ≤ 0.95 × v0.2.0 on the same split, i.e. at least 5% lower |
| **Guardrail:** WikiText-103 validation BPB | ≤ 1.02 × 1.040343 = **1.06114986** |
| **Guardrail:** WikiText-103 perplexity | reported against 23.9353; covered by the BPB guardrail |
| **Guardrail:** `mean_repeated_ngram_frac` | ≤ 1.1 × 0.0963 = **0.10593** |

**Checkpoint used for acceptance.** The training loop's own validation stream is the frozen
v0.2.0 WikiText validation stream (see §5), so `checkpoint_best.pt` is selected exactly as in
v0.2.0. Acceptance is still judged on the **final step-20000 checkpoint** with the harness above,
because the primary metric is on FineWeb-Edu, which the training loop does not see.

## 8. Artifact requirements

A result for EXP-001 is valid only if every item below exists and is hash-recorded:

1. **Dataset metadata:** for each component and the mix, the source, licence, document count, token counts, SHA-256 of every `.npy` file, and the FineWeb-Edu document-ID list.
2. **Training state:** `training_status.json` with state `completed` at step 20000, or a documented stop reason.
3. **Checkpoints and manifest:** `checkpoint_latest.pt` and `checkpoint_best.pt`, with a `MANIFEST.json` produced by `export_run_bundle` giving SHA-256, size, step and architecture for each.
4. **Evaluation reports:** harness `eval_report.json` files and `bpb.json` for both models on both validation sets.
5. **Results report:** a report in the structure of `docs/EVALUATION_v0.2.0.md` that states pass or fail against each threshold in §7 with the actual numbers, including a negative result.

## 9. Reproducibility requirements

**Launch gates.** `scripts/train_exp001.py` refuses to start unless all of these pass:

1. **Config preflight** (`scripts/validate_exp001.py`): every frozen value matches, the branch is `v0.3-exp001`, `configs/v0.2.json` is byte-identical to SHA-256 `3f539b3f2403936ce90bf570b83782f5b3c60ee59d5c1c861fb3b18d07236e7d`, and `<run dir>/tokenizer/shnu_bpe.json` hashes to the frozen tokenizer SHA-256.
2. **Run directory.** A fresh start needs an empty `checkpoints/`. `--resume` needs EXP-001's own `checkpoint_latest.pt` (config version `v0.3` and matching frozen fields). Any v0.2.0 checkpoint or v0.2.0 run directory is refused.
3. **Dataset manifest** (`validate_data_manifest`):
   - every file exists and matches its recorded size and SHA-256;
   - the WikiText validation stream, and its copy used by the training loop, both hash to `058b7107…e5eddcb8`;
   - the token counts add up;
   - the WikiText train stream hashes to the pinned `8b5ec7cf…4e923124` (233,991,238 bytes, uint16), and the validation stream has its frozen size;
   - the FineWeb-Edu source identity is pinned (`revision` for a Hub download, or `source_export_sha256` for a local export) and matches the manifest;
   - every reviewed hash is pinned in `configs/v0.3-exp001.json`: FineWeb-Edu train, mix train, FineWeb-Edu held-out, and both document-ID lists.

   The FineWeb-Edu, mix and held-out pins are `null` today, so **training is currently impossible by design** until the data has been prepared and its manifest reviewed.
4. **Explicit confirmation:** the `--confirm-reviewed` flag. `--preflight-only` runs gates 1–3 and stops.

**Other requirements:**

- **Config:** the run uses the `shnu_config` block of `configs/v0.3-exp001.json` (loaded by the launcher; the full file is not a flat `ShnuConfig`), with no command-line overrides of any frozen field.
- **Run identity:** the status file is `<run dir>/runs/shnu_v0.3_exp001/training_status.json`, with `run_name` `shnu_v0.3_exp001`. v0.2 behaviour is unchanged: `TrainingStatus` and `resume_training` still default to `shnu_v0.2`.
- **Commit:** the git commit of the code used for training is recorded in `training_status.json`, as the existing resume pipeline already does.

**Derived from code plus artifacts.** `train_val_split` takes the last int(n × val_ratio) tokens as

the last train token is not `<eos>`, so one WikiText document is cut across the boundary. Train and
validation share no tokens, but that one document's text appears on both sides. This is a v0.2
property, and EXP-001 keeps it by reusing both streams unchanged.

**Unknown.** The `min_chars` used on 2026-09-10 (the metadata does not record it; the default was
64). The exact command line, and whether the tokenizer was trained in that run or loaded, are also
not recorded. None of these matter for EXP-001, because the resulting streams are reused by hash.

## 10. Rollback and failure handling

- **v0.2.0 stays untouched.** Its tag, checkpoint and evaluation artifacts are never modified, whatever the outcome. The validator refuses an output directory or checkpoint that belongs to v0.2.0.
- **If preflight fails,** do not start. Fix the cause and re-review; never edit a frozen value to make the validator pass.
- **If training is interrupted,** resume only with `scripts/train_exp001.py --resume`, which checks that the checkpoint is EXP-001's own and then uses the existing fail-safe resume path. Never restart silently from scratch, and never resume from a v0.2.0 checkpoint.
- **If the primary threshold fails,** record a negative result for this form of the hypothesis at this scale and budget. Do not extend the budget or change thresholds after results are seen.
- **If a guardrail fails,** record the failure alongside the primary result; EXP-001 does not replace v0.2.0 as the baseline.
- **If the data or licence check fails** (licence change, SHA mismatch, leakage between the held-out and training slices), stop before training and re-register the dataset plan.
